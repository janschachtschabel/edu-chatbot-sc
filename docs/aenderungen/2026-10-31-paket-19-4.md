# Änderungsnotiz — Paket 19-4: Datenbank und Last

Stand 2026-10-31 · Plan [`docs/plans/2026-10-31-paket-19-audit-befunde.md`](../plans/2026-10-31-paket-19-audit-befunde.md) ·
Befunde [`docs/audits/2026-10-31-audit.md`](../audits/2026-10-31-audit.md) (H-5, M-10, M-1, M-11, N-26–N-29, N-31)

**Warum:** Unter Last und bei mehreren Kopien endeten Züge falsch, ohne dass es im Log stand.
Ein Zug hielt seine Datenbank-Verbindung über alle LLM-Aufrufe (ab 16 gleichzeitigen Zügen je
Kopie wartete der nächste 30 s, und die Sitzungssperre konnte verfallen); keine Verbindung hatte
eine Frist; eine Kopie, die eine Benachrichtigung verpasste, las dauerhaft alte Konfiguration —
auch die Datenschutz-Schalter.

| Was | Wie |
|---|---|
| Verbindung vor dem LLM frei (H-5) | Eine Lese-Transaktion des Zugs wird mit `commit()` geschlossen (`db/verbindung.py`, gelesene Objekte bleiben gültig): nach jedem Knoten des Zug-Graphen, nach dem Gedächtnis-Lesen in `assess`, in `setup` vor der Zustimmungs-Prüfung (LLM), nach den RAG-Abfragen (Muster- und Agent-Weg) und vor der Einbettung beim Import (`ingest_document`, `embed_missing_chunks`) |
| Eigene Engine der Sitzungssperre (H-5) | Pool 2 + 2 nur für Nehmen, Verlängern, Freigeben der Chat-Züge (`app.state.sperr_engine`, Lebenszyklus in `main`). Im Cluster unverändert in Postgres |
| Pool-Vorgabe (H-5) | geprüft, bleibt 5 + 10: ein Zug belegt eine Verbindung jetzt nur noch während der Abfragen. Anheben hätte `max_connections` im Cluster früher erschöpft |
| DB-Fristen (M-10) | je Verbindung `statement_timeout` 60 s, `idle_in_transaction_session_timeout` 300 s, `lock_timeout` 30 s (Server) und `command_timeout` 90 s (Client, fängt auch eine Netzpartition ohne RST). Die Server-Fristen per `SET` nach dem Verbindungsaufbau. VACUUM im Studio hebt Anweisungs- und Sperrfrist für sich auf (30 min) und stellt sie danach wieder her. Die Kommandozeile (`boerdi …`) baut ihre Engine ohne Fristen; Alembic hat seine eigene |
| Sitzungssperre (M-10, N-28) | Frist 10 s je Abfrage (Nehmen, Verlängern, Freigeben); das Nehmen steht im `try`, ein Abbruch direkt danach gibt mit dem eigenen `owner` frei statt die Sitzung 60 s „beschäftigt“ zu lassen |
| Config-Abgleich (M-1) | gescheiterter Refresh: bis 5 Versuche mit wachsender Pause (1 → 16 s), danach gemerkt; alle 60 s Versionsabgleich (`SELECT area, version`) lädt Veraltetes, Fehlendes, Gelöschtes und Gemerktes nach; LISTEN-Verbindung alle 15 s mit `SELECT 1` (Frist 5 s) geprüft, sonst Neuaufbau samt Neuladen |
| `/ready` (M-1) | Grund `konfiguration`, wenn weder LISTEN steht noch ein Versionsabgleich in drei Takten (180 s) gelang. Ein kurzer Abriss des Listeners allein nimmt keine Kopie aus dem Dienst |
| Herunterfahren | Abgleich, Nachladen und Listener teilen sich die eine Abbruchfrist (`ABBRUCH_FRIST_S`) — die Summe steigt nicht |
| Wiederverbindung (N-29) | der Neulade-Lauf nach einer Wiederverbindung hat eine starke Referenz |
| Werkzeug-Cache (M-11) | zusätzlich nach Größe gedeckelt: Summe 20 Mio. Zeichen (älteste weichen), ein Eintrag über 1 Mio. Zeichen wird nicht gespeichert; Diagnose zeigt `chars` |
| LLM-Strom (N-26) | wird in jedem Fall geschlossen (`aclose`), auch bei Abbruch durch Agent-Frist oder auflegenden Client |
| MCP-Discovery (N-27) | Gesamtfrist `MCP_CALL_TIMEOUT_S` wie beim Werkzeugaufruf (vorher bis 5 min je schweigendem Fremdserver) |
| Umwandlung (N-31) | der Platz „eine Umwandlung zugleich“ wird erst frei, wenn Thread und Kindprozess fertig sind; der Abbruch erreicht den Aufrufer trotzdem sofort |

## Was sich im Betrieb ändert

| Was | Muss | Kann |
|---|---|---|
| Image | neu bauen; keine Migration | |
| Postgres | `max_connections ≥ N × (DB_POOL_SIZE + DB_MAX_OVERFLOW + 6) + Reserve` (Vorgaben: N × 21, bisher N × 17): je Kopie bis 4 Verbindungen der Sitzungssperre mehr; beim Rolling Update zählen die Surge-Pods mit | |
| Neue Env-Variablen | | `DB_STATEMENT_TIMEOUT_S` (60), `DB_COMMAND_TIMEOUT_S` (90), `DB_IDLE_IN_TRANSACTION_TIMEOUT_S` (300), `DB_LOCK_TIMEOUT_S` (30) — Sekunden, 0 = aus; `MCP_TOOL_CACHE_MAX_CHARS` (20000000), `MCP_TOOL_CACHE_MAX_ENTRY_CHARS` (1000000) — Zeichen, 0 = ohne Deckel. Stehen in `deploy/.env.example`, `compose.prod.yml`, `helm/values.example.yaml` |
| PgBouncer | nur Session-Modus (wie bisher wegen LISTEN); die Server-Fristen setzt die App per `SET` nach dem Verbinden, im Startpaket steht keiner — PgBouncer lehnt unbekannte Startparameter ab | |
| Lange Wartungsläufe | | Kommandozeile nutzen (ohne Fristen); im Studio hat nur VACUUM eine eigene Frist |

## Review-Nachbesserungen (2026-10-31)

| Befund | Behoben |
|---|---|
| HOCH: Server-Fristen als asyncpg-`server_settings` im Startpaket — PgBouncer lehnt sie ab („unsupported startup parameter“), kein Pod startet | `SET statement_timeout/idle_in_transaction_session_timeout/lock_timeout` im SQLAlchemy-Ereignis `connect`; im Startpaket nur noch `command_timeout` (clientseitig) |
| `ConfigStore.stop()` konnte während der Abbruchfrist neue Aufgaben starten | Merker `_gestoppt` zuerst; Benachrichtigung, Wiederverbindung und Abgleich starten danach nichts mehr. Die geteilte Frist bleibt |
| VACUUM wartete mit `lock_timeout` auf Tabellensperren | auch `lock_timeout` aufgehoben; beide Werte werden danach wiederhergestellt (nicht `RESET` — das fiele auf die Vorgabe des Servers zurück) |
| Freigabe der Zug-Verbindung schrieb ungespeicherte Objekte still fest | WARNING mit den Zahlen (ohne Inhalt), wenn `new`/`dirty`/`deleted` nicht leer sind |
| Ausgeschöpfter Pool nur an der Fehlerblase zu erkennen | Pool der App meldet (gedrosselt, 60 s) eine Wartezeit ab 1 s und das Scheitern an `pool_timeout` |
| Sitzungssperre: „beschäftigt“ löste ein überflüssiges DELETE aus | freigegeben wird nur, wenn ein Nehmen lief und nicht sicher `False` lieferte |
| Formel der Verbindungen | allgemein `N × (DB_POOL_SIZE + DB_MAX_OVERFLOW + 6) + Reserve`, Surge-Pods beim Rolling Update mitzählen (Checkliste, Übergabe, Steckbrief, Helm, `.env.example`) |

Tests: `test_db_pool` (Startpaket ohne Server-Fristen, `SET`-Anweisungen), `test_db_fristen_pg`
(SHOW-Werte über `SET`, Pool-Warnung, VACUUM stellt Anweisungs- und Sperrfrist wieder her),
`test_zug_verbindung_pg` (Warnung bei ungespeicherten Objekten), `test_sitzungssperre_fristen`
(kein DELETE nach „beschäftigt“), `test_config_abgleich` (nach `stop()` keine neuen Aufgaben;
Warte-Helfer nach der Uhr statt nach Schritten — unter Windows kehrt `sleep(0.005)` oft sofort
zurück).
